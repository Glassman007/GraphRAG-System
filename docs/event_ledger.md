# Event Ledger

`Event` is the append-oriented history primitive. It is not a full event-sourcing implementation yet; Phase 2 establishes the data contract needed by replay, resumability and process reconstruction.

## Core event types

- `SITUATION_CREATED`
- `PLAN_CREATED`
- `TASK_CREATED`
- `TASK_CLAIMED`
- `TASK_COMPLETED`
- `EVIDENCE_FOUND`
- `HYPOTHESIS_CREATED`
- `HYPOTHESIS_REJECTED`
- `CLAIM_CREATED`
- `DECISION_CREATED`
- `ACTION_PROPOSED`
- `APPROVAL_REQUESTED`
- `ACTION_EXECUTED`
- `OUTCOME_OBSERVED`
- `DEPLOYMENT_STARTED` (fixture-specific extension)

## Links

- `Event -[:ABOUT]-> Plan|Incident|Task|Claim|Evidence|Decision|Action|System|Deployment|Change`
- `Event -[:PERFORMED_BY]-> Person|Agent|Team`
- `Event -[:BEFORE]-> Event` when explicit ordering matters
- `Event -[:DERIVED_FROM]-> DataSource|Document` when imported

## Invariants

1. Event IDs are immutable.
2. `occurred_at` is the time of the represented event, not ingestion time.
3. Later corrections append new events/claims; they do not rewrite past events.
4. Side-effect execution must eventually be paired with stable `Action.idempotency_key` and one terminal `ACTION_EXECUTED` event.
5. Replay always uses the historical graph available up to the replay timestamp.


## Phase 5 planner events

Phase 5 writes `PLAN_CREATED` and reuses the existing `TASK_CREATED` event. IDs are deterministic (`EVT-{plan_id}-CREATED`, `EVT-{task_id}-CREATED`), so recomputing unchanged state does not append duplicate creation events. The deterministic planner is represented as `AGENT-DETERMINISTIC-PLANNER` only for provenance; it is not an autonomous execution worker. No TASK_CLAIMED, TASK_COMPLETED, ACTION_EXECUTED, handoff or lock event is generated by Phase 5.

## Phase 6 coordination events

Phase 6 extends the ledger only for real coordination state transitions. Depending on the path taken, the system may append:

- `TASK_CLAIMED`
- `TASK_STARTED`
- `CHECKPOINT_SAVED`
- `EXECUTION_RESUMED`
- `TASK_BLOCKED`
- `TASK_COMPLETED`
- `FINDING_CREATED`
- `FINDING_VERIFIED`
- `FINDING_REJECTED`
- `HANDOFF_CREATED`
- `HANDOFF_ACCEPTED`
- `HANDOFF_REJECTED`
- `BRANCH_CREATED`
- `BRANCH_VALIDATED`
- `BRANCH_MERGED`
- `BRANCH_REJECTED`
- `LOCK_ACQUIRED`
- `LOCK_RELEASED`
- `CONTENTION_DETECTED`
- `DEADLOCK_DETECTED`
- `ACTION_PROPOSED`
- `ACTION_GOVERNANCE_ALLOWED`
- `ACTION_GOVERNANCE_DENIED`
- `ACTION_STARTED`
- `ACTION_SUCCEEDED`
- `ACTION_FAILED`
- `MEMORY_COMPACTED`

Events retain `occurred_at`, actor/generator where available, and `ABOUT` links to the Task/Execution/Finding/Handoff/Branch/Action/Attempt/CompactionRecord involved. Checkpoints store only deterministic resume state; no private model chain-of-thought is persisted.

The event ledger remains an audit/replay layer, not the sole coordination store. Current ownership, locks, checkpoints, branch state and action attempts are reconstructed from their typed graph objects and relationships in FalkorDB.
